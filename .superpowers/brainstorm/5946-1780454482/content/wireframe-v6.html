Prototype is clickable — the top/sub-tabs, HQ nav, terminal tabs, ticket cards, and watch/start buttons all navigate between screens.

System map — how the pieces talk

Every claude+ session is a thin pass-through wrapper around Claude that mirrors all traffic to an event bus. Command HQ subscribes to that bus to render live state; control commands from the web flow back down into the running session.

① claude+ instance (per repo)

One persistent claude+ per repo, named for the repo, runs as a background daemon. Holds several inner claude sessions (sub-tabs). Your terminal attaches to it; closing the terminal leaves it running. claude+ ls lists them. Adds tabs: Session · Tickets · Agents · Stream.

Local agent config

Reads/writes ~/.claude/ (agents, skills, MCP). Stays in sync with the user's real Claude Code setup.

events →
← control

② Event bus + store

Ingests session events (messages, tool calls, status, cost). Append-only log per session + current-state cache. The single source of truth.

③ Control gateway

Routes inbound commands (inject message, pause, approve) to the right live session. The web calls this; any future client (Telegram, mobile) would too.

④ Command HQ (web)
Projects · tickets (source of truth) · live + historical sessions · agent setups. Read model from the event store, write via the control gateway.
⑤ Ticket store
Tickets live in HQ's DB (not local files). The chain ticket→session→branch→PR is tracked here; the terminal reads/writes via the HQ API so every machine sees the same backlog.
⑥ GitHub repos
One repo = one project. Root holds PRD.md (goal + the repo's objectives, which link up to company RCDO) + PROGRESS.md (done). Branches/PRs + weekly updates trace back to objectives.
Open question for you: does claude+ capture events by parsing the PTY stream, or by running Claude in headless/SDK mode and rendering our own TUI? The wrapper tabs below assume we own the chrome (tab bar + status line) and embed Claude's session inside it.

terminal  claude+ ls — instances & attach

Two levels: a claude+ instance is one persistent daemon bound to a repo (named for it), and each instance runs several inner claude sessions (the sub-tabs). claude+ ls lists the instances; you attach by index or just run claude+ inside a repo and it finds (or creates) that repo's instance. Like tmux ls / tmux attach, but per-repo and Claude-aware.

zsh  —  ~/projects
$ claude+ ls ⟨①⟩ list every running claude+ instance (not plain claude) # REPO SESSIONS STATE UPTIME HOST ⟨②⟩ 0 command-hq 3 ● 1 needs-input 14m matt@mbp 1 atlas-billing 1 ● running 6m matt@mbp 2 nimbus-docs 2 ○ idle 2h ci-runner-2 ───────────────────────────────────────────────────────────────── 3 instances · 6 sessions · streaming to HQ $ claude+ --session=0 ⟨③⟩ attach to instance #0 (command-hq) → opens the TUI attaching to command-hq … 3 sessions restored $ cd ~/projects/atlas-billing && claude+ ⟨④⟩ no index → match by repo ↳ found running instance #1 for atlas-billing — attaching $ cd ~/projects/new-thing && claude+ ⟨⑤⟩ no instance yet → start one ↳ no instance for new-thing — starting #3, named new-thing
⟨⑥⟩ claude+ ls instances --session=N attach by index claude+ attach-or-create for cwd repo --detach · --kill N
  • claude+ ls shows only claude+ instances — the wrappers — each a repo-bound daemon, with how many inner claude sessions it holds and an aggregate state.
  • Index + repo name — the # is what you pass to --session; the name always mirrors the repo so the list is self-describing.
  • Attach by index — claude+ --session=0 drops you into that instance's TUI (the Session tab, with its sub-tabs restored).
  • Bare claude+ in a repo — if an instance already exists for the current repo, it attaches to it instead of spawning a duplicate.
  • No instance yet — bare claude+ in a fresh repo starts a new instance named for that repo. This is the default, zero-friction path.
  • Lifecycle flags — detach leaves it running in the background (still on HQ); --kill N tears one down. Instances survive your terminal closing.
Why a daemon: for an instance to keep running (and keep streaming to HQ) after you close the terminal — and to be attachable from a second terminal or re-attachable after a disconnect — the inner claude sessions must live in a background process, with the TUI as a thin attachable client. Same architecture as tmux/TerMinal.

terminal  claude+ — Session tab

The default view, after you attach to a repo's instance. Claude runs exactly as normal; claude+ only adds the tab bar (top) and the status line (bottom). A second row of session sub-tabs runs several Claude sessions within this one repo and you switch between them. Each one auto-generates a name from what it's working on, so you never have to title them. Each is its own process, all streaming to HQ.

Architecture: tmux-style multiplexing, but scoped to one repo. The instance daemon (see claude+ ls) holds one PTY per session and the TUI renders only the focused one; the rest run in the background. Each is a full Claude process, so it's a handful-of-sessions feature — the cost roll-up keeps that visible.

terminal  claude+ — AgentForge (/startforge … /endforge)

Commands, not a panel. /startforge lands your current work to main, then branches a worktree and marks the slice; you do the work (the daemon captures the session + diff); /endforge distills it into a reusable agent — a short prompt + the minimal skills it needs — and registers it at your own scope. Promoting it org-wide is a deliberate step in Command HQ. (v1 is distiller-first: capture → distill → register. The prompt optimize/refine loop is the next increment.)

  • Two commands, no GUI — /startforge lands current work to main, then branches a worktree + start marker; /endforge distills + registers. Replaces the old fuzzy "describe an agent" Forge tab. (Aborts if current work can't land cleanly.)
  • Distiller-first v1 — capture → distill → register, end to end. The prompt optimize/refine loop (run candidates in a worktree, score, iterate) is the next increment, not v1.
  • Classify, don't block — /endforge warns if the diff isn't a coherent feature, but you can override and forge anyway.
  • Minimal skills — curated from what the session actually used; references existing skills, mints only the new ones the agent needs (registered alongside it).
  • Registers at your scope — the agent + new skills land at the author's scope; usable only by you until promoted.
  • Promotion is the quality gate — going org-wide is a deliberate human action in Command HQ, so a weak forge never auto-hits the whole org.
The loop this closes: capture a slice → distill → register at your scope → promote in HQ → config-sync drift makes it pullable org-wide → that agent runs new sessions → which can be forged again. (Backend reuses packages/backend/src/forge/; ground truth: docs/plans/command-hq/05-agentforge.md.)

  • Same data, raw. Every line here is one structured event the wrapper emits; the Session tab is these same events rendered for humans.
  • Scope toggle — merged feed across the instance's sessions, or filter to one session's stream. (Open question I raised earlier: per-session vs merged — here you get both.)
  • Controls — pause the scroll, filter by type/session, wrap long lines. Read-only; you don't act here, you observe.
  • Status events are first-class — status.change → needs_input is what flips a session to "needs input" on HQ and the Sessions list.
  • Scope + counters — which sessions are in view, total events seen, and a dropped counter (should stay 0) that proves nothing is being lost on the way to HQ.
  • Export — dump the event log (the append-only record per session) for debugging or replay.
Product call for you: Stream is the most optional of the four tabs — end users mostly want the conversation, not the wire format. Options: keep it a first-class tab (shown here), demote it to a hidden debug view behind a keybind (e.g. ⌃D), or drop it from the terminal and only expose the raw feed on HQ. Easy to change.

web  Command HQ — Project › Weekly Update

The output of the /weekly-update skill. You run it, it interviews you about next week's goals and pushes back to check them against this repo's fixed high-level goals, then auto-writes two halves: Reconciliation — last week's plan vs. actual read from git history (what got done, which requirement items it checked off, how much it moved progress) — and the validated Plan next week. It moves through a lifecycle: DRAFT → LOCKED → RECONCILING → RECONCILED.

  • Org scope (all users) — the broadest tier; everyone inherits these. Edits are admin-gated so one team can't break everyone.
