Organization Management (onboarding — create or join an org on first sign-in)

Membership in an organization is now a real, DB-backed fact a user can lack. On first sign-in a user with no org is forced through an OrgGate to either create an org (name + password) or join an existing one (exact name + password) before the app renders. From then on every org-scoped read/write is keyed to the org the user chose — objectives, the Definition of Done, and the skills/agents catalog — and the catalog stays partitionable by org id and by user id.

Problem frame

Until now a user's org came entirely from the Cognito token claim custom:org, and a pre-token-generation Lambda defaults a missing claim to personasearch (infra/lib/auth-stack.ts). The consequence: every account always "had" an org, so no one was ever genuinely unaffiliated and there was no onboarding step — a fresh Google sign-in was silently authorized into one shared org. That is fine for a single-tenant demo but wrong the moment two organizations share the deployment: there is no membership decision, no per-org password gate, and no way for a user to say "I belong here, not there." We make membership DB-driven via the user's PROFILE record so a user can have no org and must onboard, and so the org they end up in is a recorded choice rather than a token default.

Key decisions

  • Membership lives on the PROFILE record, not the token claim. The source of truth is USER#<uid>/PROFILE.org. The Cognito custom:org claim is kept only as a back-compat fallback (see effectiveOrg); a user with no profile org is treated as genuinely org-less and routed into onboarding.
  • GET /me drives the OrgGate. After login the web calls GET /me; when it returns org: null the OrgGate intercepts and forces create/join before the app renders any org-scoped screen. There is no way to skip past it into the app.
  • Create org = name + password. The password is scrypt-hashed (salt + hash, never the plaintext) into the ORG#<name>/META record via a conditional create, so a name collision is a clean 409 rather than an overwrite. The creator becomes the org admin (their PROFILE gets admin: true alongside org).
  • Join org = EXACT name + password. The user must type the existing org's name exactly; the password is verified against the stored scrypt hash. Any failure — unknown name or wrong password — returns a single generic 403 with one message, so the endpoint can't be used to enumerate which org names exist.
  • effectiveOrg(event, repo) = profile.org ?? token-claim-org. This threads the chosen org through every org-scoped handler in one place. The token fallback is deliberate: it keeps existing handler tests (which seed no profile) passing and lets device-token / wrapper traffic — which carries the claim but no onboarding flow — keep resolving an org, while real onboarded web users get the org they picked.
  • Data partitions by org id AND user id. Org-global state lives under ORG#<org> (objectives RCDO#…, the DoD CONFIG#DOD, and the new org record META). The skills/agents catalog is keyed SCOPE#org#<id> / SCOPE#user#<id> (scopeId/agentKey/skillKey in db/keys.ts), so the catalog is already partitionable by org id and by user id — onboarding just supplies the org id every query scopes to.

Actors

  • New user (no org) — signs in for the first time; GET /me returns org: null; the OrgGate forces a create-or-join choice before anything else loads.
  • Org creator — supplies a new name + password, lands the ORG#<name>/META record, and becomes the org admin in the same step.
  • Joining user — supplies an existing org's exact name + password and, on a match, has their PROFILE org set; a mismatch is one generic 403.
  • Org admin — the creator (and anyone later granted admin); admin-gated writes (the catalog REST) are authorized against this flag.

User flow

  • F1 — Sign in. The user authenticates (Google federated sign-in, as today).
  • F2 — Resolve membership. The web calls GET /me, which reads the PROFILE record and returns org: string | null.
  • F3 — OrgGate (only when org is null). The user must create (name + password → POST /orgs) or join (exact name + password → POST /orgs/join). On success the PROFILE's org (and, for a creator, admin) is set.
  • F4 — App renders org-scoped. With profile.org set, effectiveOrg resolves the chosen org and every subsequent read/write is scoped to it.

Data model

The org record lives in the same ORG#<org> partition that already holds objectives (RCDO#…) and the Definition of Done (CONFIG#DOD), under SK META: 

ORG#<name> / META = {
  name,                 // the org's exact name (also the partition id)
  createdBy,            // { userId, name } of the creator
  createdAt,            // ISO timestamp
  passwordSalt,         // scrypt salt — never returned to clients
  passwordHash          // scrypt hash  — never returned to clients
}

Membership hangs off the existing user PROFILE record (USER#<uid>/PROFILE, userKey(userId)): 

USER#<uid> / PROFILE = {
  userId,
  name?,                // display name, if known
  org?,                 // the chosen org — null/absent until onboarded
  admin?                // true for the org creator
}

The passwordSalt/passwordHash fields are server-only: they are written on create, read only to verify a join, and never serialized back to any client. The DTO returned by GET /me exposes only { userId, name?, org, admin? }.

REST contract

  • GET /me → 200 { userId, name?, org: string | null, admin? }. The org: null case is what the OrgGate keys on.
  • POST /orgs { name, password } → 201 { org, admin: true } on create (creator becomes admin); 409 if the org name already exists (conditional-create collision); 400 on a missing/invalid name or password.
  • POST /orgs/join { name, password } → 200 { org, admin } on an exact-name + correct-password match; 403 'invalid organization name or password' — one generic message for both an unknown name and a wrong password (no enumeration); 400 on a missing/invalid body.

All three set or read the PROFILE org field, which is the single fact effectiveOrg consults to scope the rest of the API.

Status

  • Built: DB-driven membership on the PROFILE record; GET /me returning org: null for un-onboarded users; POST /orgs (scrypt-hashed, conditional-create, 409 on collision, creator-as-admin) and POST /orgs/join (exact name + password, one generic 403); the web OrgGate that forces create/join on org: null; effectiveOrg(event, repo) scoping org data by the chosen org with the token-claim fallback for back-compat + device tokens.
  • Open: richer membership management (invite links, multiple admins, leave/ remove, org rename); rate-limiting the join endpoint; password rotation.
