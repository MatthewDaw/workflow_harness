Memory Sync (Claude Code project memories → Command HQ)

Claude Code persists small per-project "memories" — short markdown facts it learns about a repo (conventions, gotchas, where things live) — as files under the project's memory/ directory. Memory Sync reconciles that directory up to Command HQ automatically as Claude writes it, so the whole team can see what Claude has learned about a project. Memories are stored per user (each stamped with its author) and surfaced on a new per-user, grouped/filterable Memories tab on the Project Details page.

Problem frame

Claude Code already saves per-project memories locally, but they never left the developer's machine. Each memory is a small fact Claude decided was worth keeping for next time — and they accumulated silently in one person's memory/ directory. The team had no visibility into what Claude had learned about a project: the same lessons were re-derived per developer, and a teammate opening the repo couldn't see the context Claude was already operating with. The capture path the daemon uses for sessions doesn't cover these files, so the knowledge stayed trapped on disk. What's missing is a way to mirror that local memory set up to HQ as it changes, attributed to whoever authored it, and to read it back grouped by author on the project.

Key decisions

  • Automatic, daemon-driven. The claude+ daemon reconciles the project's memory/ directory up to HQ on the end-of-turn Stop hook (debounced), so memories sync as Claude saves them with no manual action from the developer.
  • Per-user storage. Every memory is stamped with its author. The data model is PROJ#<projectId> / MEM#<userId>#<name> — one project is one partition, and a per-author SK prefix (MEM#<userId>#) scopes the reconcile so one developer's sync never touches another's memories.
  • Full reconcile (HQ mirrors disk). The daemon PUTs the whole current set for the caller; adds and updates propagate, and so do deletions — a memory removed on disk is removed from HQ. An empty array clears the caller's set entirely. HQ is a mirror of what's on disk, not an accumulating log.
  • Surfaced per user. A new Memories tab on Project Details shows the project's memories grouped and filterable by author, so a teammate can read exactly what Claude learned for each developer on the project.
  • Shared route, two principals. The GET (web, Cognito JWT) and the PUT (daemon, HS256 device token) share one route via an HttpNoneAuthorizer plus an in-Lambda resolvePrincipal — exactly like the weekly routes — so the same handler accepts either credential and scopes off the resolved principal.

Actors

  • The developer (author) — runs Claude Code on the project; their local memory/ directory is the source of truth that gets mirrored to HQ, stamped under their userId.
  • Teammates viewing the project — open the Memories tab in Command HQ to read what Claude learned, grouped/filtered by author.
  • The claude+ daemon — watches the memory/ directory and, on the debounced Stop hook, reconciles the current set up to HQ via the PUT route using the device token.

Data model

Each memory is one record in the project's partition, sub-keyed by author and name: PROJ#<projectId> / MEM#<userId>#<name> (see platform_architecture.html for the single-table model). The record holds { projectId, userId, userName?, name, description?, type?, content, updatedAt }:

  • projectId / userId. Identify the owning project partition and the author the reconcile scopes to; together with name they form the record key.
  • userName?. The author's display name, stamped so the Memories tab can group/label by person without a second lookup.
  • name. The memory's file-derived identifier (unique per author within the project).
  • description? / type?. Optional metadata; type is one of user | feedback | project | reference.
  • content. The memory body — the markdown fact itself.
  • updatedAt. Epoch-ms of the sync that last wrote this memory.

REST contract

Both verbs live on one route, owner-gated, sharing the HttpNoneAuthorizer + resolvePrincipal pattern:

  • GET /projects/:id/memories → 200 { memories: Memory[] }. Owner-gated; returns all authors' memories for the project (the tab groups them client-side). Authenticated with the web Cognito JWT.
  • PUT /projects/:id/memories with body { memories: [{ name, description?, type?, content }] } → 200 { memories }. Reconciles the caller's set only: it replaces every MEM#<userId># record for the resolved principal — PUTs each item and deletes the author's existing memories not in the set, so an empty array clears it. The server stamps projectId, userId, userName, and updatedAt; the daemon sends only the on-disk fields. Authenticated with the daemon's HS256 device token.
